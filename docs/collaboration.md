# 시평 하네스 기반 개발 방법

하네스는 팀원이 Codex에 작업을 맡길 때 사용하는 공통 지침, 협업 절차, 자동 검사 환경입니다. 각자의 Codex 세션에서 작업해도 GitHub에 남긴 Issue, PR, 문서를 읽으면 같은 범위와 완료 기준을 확인할 수 있습니다.

## 각 구성의 역할

| 구성 | 역할 |
| --- | --- |
| GitHub Issue | 담당자, 목표, 수정 범위, 의존성, 마감, 완료 조건을 기록합니다. 주간 회의에서 승인한 범위가 작업 기준입니다. |
| AGENTS.md와 설계 자료 | 루트 지침에서 공통 절차를, 앱 지침에서 역할별 규칙을 읽습니다. 해당 기능의 API·디자인 부분만 확인합니다. FE는 합의한 API 계약으로 Mock을 만들고 BE는 같은 계약을 구현합니다. |
| PR과 CI | PR에는 Issue, 변경 내용, 검증 결과, 남은 항목을 남깁니다. CI는 NestJS의 타입 검사·테스트·빌드를 자동 실행하도록 설정합니다. |

## Issue 하나를 진행하는 순서

저장소 폴더에서 Codex를 열고 담당 Issue를 알려주세요. 팀에서 합의한 범위와 검증 결과는 Issue나 PR에 남깁니다.

| 순서 | 할 일 |
| --- | --- |
| 1. 범위 확인 | 담당 Issue와 앱별 AGENTS.md, 관련 API·디자인 문서만 확인합니다. 완료 기준이나 담당 범위가 모호하면 필요한 질문만 합니다. |
| 2. 작업 계획 | 목표, 수정 경로, 선행 조건, 검증 방법을 확인합니다. |
| 3. 개발·검증 | Issue의 범위를 작업 브랜치에서 구현합니다. 계약이나 공통 파일을 바꿔야 하면 영향과 결정할 내용을 Issue에 남깁니다. |
| 4. 결과 보고 | 바뀐 내용, 실행한 검사와 결과, 남은 검증을 보고합니다. |
| 5. PR 게시 | 브랜치를 푸시하고 Issue를 연결한 PR을 올립니다. |

## Codex에 붙여넣을 문장

> Issue #번호를 맡았어. 관련 지침과 문서를 읽고 필요한 질문만 해줘. Issue의 범위에 맞춰 작업하고, 수정 경로와 검증 결과를 정리해줘.

## 짧은 보고 예시

- **계획** — 로그인 화면 구현. `apps/web` 로그인 화면 수정. 인증 API 경로 합의가 필요하며 성공·실패 화면을 Mock으로 검증.
- **결과** — 로그인 화면과 실패 안내 구현. 타입 검사와 Mock 검증 통과. 실제 API 연동 검증 대기.

Issue는 시작할 때 `In Progress`, PR을 올리면 `In Review`, 병합 후 완료 기준을 확인하면 `Done`으로 갱신합니다. 작업이 막히면 `Blocked`와 재개 조건을 기록합니다.

## 팀에 적용하고 확인하는 방법

1. 초기 세팅 PR에서 GitHub Actions가 실행되는지 확인합니다. 현재 저장소의 지침과 CI 설정은 로컬 초기 세팅 브랜치에 있습니다.
2. 팀 합의 후 `main` 병합에 PR, 팀원 리뷰 1명, CI 통과를 요구하도록 설정합니다. GitHub에서 병합 조건을 검사합니다. [GitHub 브랜치 보호 문서](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)
3. 첫 작업에서 Issue의 완료 조건과 구현을 대조하고, 검증 결과를 PR에 기록합니다. 다른 팀원이 Issue와 PR만 읽고 범위와 결과를 파악할 수 있는지 확인합니다.
4. 주간 회의에서 확정 Issue의 완료·차단 상태와 통합 결과를 확인합니다. 같은 절차가 반복될 때 Skill로 정리할지 결정합니다.
